生产级 Agent 六层模型

对照火山引擎 Force 大会原文，拆解一个 Agent 从“会回答”走向“可进入组织生产”的必要结构。

思航研究 2026 年 7 月 2 日 Agent 架构 · 火山引擎

生产级 Agent 不是一个模型外加几个工具，而是一组相互依赖的能力层。越靠下的层越接近技术地基，越靠上的层越接近组织价值。任何一层缺失，问题都会在更高层被放大。

核心判断：下层决定 Agent 能不能工作，上层决定 Agent 能不能被企业长期使用。

Framework

框架总览

层次名称管理层真正需要回答的问题
L1模型智能层模型是否足够理解、规划、推理、生成和纠错？
L2上下文与记忆层Agent 是否理解企业、客户、业务规则和历史经验？
L3工具与系统连接层Agent 是否能连接真实业务系统，而不是停留在对话框？
L4运行与执行层Agent 是否能安全执行长链路任务，并支持恢复、并发和回写？
L5安全与治理层身份、权限、审计、密钥、数据边界和高风险操作是否可控？
L6组织运营层Agent 是否可复用、可衡量、可协同、可持续优化？
L1

模型智能层

模型是否足够理解、规划、推理、生成和纠错？

对应能力

  • 理解：Seed 2.1 强化图像、视频的细颗粒度理解，提高 GUI 与 UI 操作稳定性；CG 5.0 Pro 支持通过点选、圈选、箭头和草图表达编辑意图。
  • 规划：模型需要理解角色、形成长期计划并处理错误。游戏开发案例已经覆盖策划、素材到成品的自主流程规划。
  • 推理：从平面户型图恢复可漫游三维空间，或从看板草图推断页面结构、布局与未写明的交互。
  • 生成：文本、图像、视频、语音和 3D 建模逐渐进入同一任务链，生成不再是孤立输出。
  • 纠错：模型能够检测动作序列、代码或页面中的错误，并在执行过程中修正。
关键判断

模型能力是 Agent 的地基。L1 不强，上层工程会不断用规则、提示词和人工复核填补缺口，系统复杂度会快速上升。

L2

上下文与记忆层

Agent 是否理解企业、客户、业务规则和历史经验？

知识与记忆

销售拜访 Agent 需要沉淀客户历史、产品用量、沟通记录与成功案例；安踏案例则把六年积累的百万级产品数据，与版型、材质、配色及穿搭认知结合。上下文不是附加材料，而是 Agent 理解企业的方式。

OpenViking 设计解决的问题
万物皆为文件把分散上下文转为结构化文件系统。
目录递归检索沿业务层级寻找更匹配、语境更完整的数据。
记忆自我迭代记住偏好、纠正错误，让 Agent 随使用持续改善。
按需渐进加载按摘要、概要、细节加载，减少信息噪音和 Token 消耗。
多租户隔离隔离企业、团队、业务与用户之间的数据边界。
关键判断

企业知识的价值首先来自结构，而不是总量。平铺的数据越多，越可能让 Agent 在检索时丢失真实业务语境。

L3

工具与系统连接层

Agent 是否能进入真实业务系统，而不是停留在对话框？

系统连接

API、Skills 与 Gateway 将 Agent 接入 CRM、BI、案例库、日程、搜索、数据库和企业网盘。多模态输入也必须转化为可写回业务系统的结构化信息，例如把销售会谈自动记录到 CRM，并触发后续分析。

  • 连接 CRM、BI、日程与案例库，形成跨系统任务链。
  • 接入实时搜索、专业数据集和企业内部数据库。
  • 把语音、图像等多模态输入转成业务系统可消费的数据。
  • 通过版权或合规平台约束生成内容的实际使用范围。
关键判断

L3 是 Demo Agent 与生产 Agent 的分界线。只有进入既有系统，模型输出才可能真正推动流程、修改状态并产生业务结果。

L4

运行与执行层

Agent 是否能安全跑完长链路任务，并支持恢复、并发和回写？

从调用工具到跑完流程

  • 编排：把拜访前准备、拜访中记录、拜访后总结和商机更新串成完整流程。
  • 长时任务：任务可能持续两到三小时，需要保存业务状态、快照休眠并在中断后恢复。
  • 沙箱：任务在明确身份、权限与隔离环境内运行，文件和计算资源按需挂载。
  • 并发：运行时既要支持单个 Agent，也要能弹性拉起大规模实例。
  • 回写：执行结果必须更新 CRM、审批或其他业务系统，形成闭环。
关键判断

长时任务的差异化能力不只是“跑得久”，而是状态可保存、任务可恢复。但恢复之后如何保证上下文和外部系统状态一致，仍是容易被忽略的问题。

L5

安全与治理层

身份、权限、审计、密钥、数据边界和高风险操作是否可控？

可信调用链

Identity 与 Policy 决定 Agent 能看到什么、可以做什么。通过飞书、企微或钉钉传递组织身份，用户、Agent、工具和企业服务才能形成可审计的调用链。

  • 以最小权限完成任务，并把高风险操作限制在明确授权范围。
  • 记录每次工具调用、数据访问、状态修改与人工确认。
  • 隔离企业、团队、业务和用户数据，保护密钥与运行环境。
  • 允许治理系统在执行中拦截，而不是只在事后生成日志。
关键判断

技术可以执行 Policy，但无法替企业决定 Policy。最小权限由 IT、业务负责人还是法务定义，是一个组织权责问题，比权限系统本身更难。

L6

组织运营层

Agent 是否可复用、可衡量、可协同并持续优化？

从单点工具到组织资产

  • 可衡量：通过 Evaluation 与 Observability 持续验证过程和结果，回答 ROI 问题。
  • 可复用：验证过的核心 Agent 可以复制到相邻场景，经验与流程沉淀为组织资产。
  • 可协同：研发、产品、测试与业务角色在同一条工作流中持续配合。
  • 可优化：评测、运行数据与记忆系统共同构成持续改进回路。
角色关注点适配形态
业务团队机会与结果开箱即用的 Agent 软件
研发团队碎片化需求零代码或低代码平台
IT 团队制度与安全高代码平台与统一治理
管理层投资回报率统一调度和治理看板
关键判断

“AI 员工管理体系”是一个有启发性的类比，但不能照搬人力资源管理。AI 不会疲劳，却会幻觉和产生系统性偏差，因此它需要不同的评价、授权与纠错机制。

Dependencies

六层之间的依赖关系

  1. L6
    组织运营层

    依赖治理数据、执行记录和经验沉淀。

  2. L5
    安全与治理层

    依赖执行环境、系统边界和数据边界。

  3. L4
    运行与执行层

    依赖系统连接、业务上下文和模型智能。

  4. L3
    工具与系统连接层

    依赖 Agent 知道连接什么，以及如何正确调用。

  5. L2
    上下文与记忆层

    依赖模型能够理解、筛选和使用上下文。

  6. L1
    模型智能层

    依赖未单独列出的 L0 基础设施。

刚性约束：L1 不够强，L2 记得再多也无法正确理解；L5 没做好，L6 的可衡量就会建立在不可信的审计数据上。

Reflection

为什么这个框架更好用

  1. 把连接与执行分开。

    L3 回答“能不能碰到系统”，L4 回答“碰到之后能不能把任务跑完”。两者的工程约束不同。

  2. 把安全治理独立成层。

    安全不是基础设施的静态属性，而是贯穿数据、工具、执行和组织运营的横切能力。

  3. 每层都对应管理层问题。

    技术分层因此变成决策工具：管理者可以定位 Agent 失败究竟来自模型、数据、连接、执行、治理还是运营。

本文根据个人会议笔记整理，框架来源为生产级 Agent L1–L6 模型，并对照火山引擎 Force 大会 6 月 24 日上午场内容提炼。
